# 维护工作流

> V1.0.1 · 2026-11-10 · 决定卡说明等待状态，保留独立验收的具体拒收原因。

## 职责与范围

`maintenance` 是外层插件，按计划、决定、执行、验收四个阶段交接。既有故障和本人提出的任务使用同一套阶段控制。队列、并发、去重、失败重派、决定卡和到期唤醒仍由中台负责，不增加后台服务，不修改内核或 `/v1` 协议。

项目提供可信的事实检查、工作区准备、执行前检查和验收入口。模型输出只作为方案与证据材料，不能选择程序、目录、权限或 Agent。岗位的程序、模型、权限和工作目录由项目配置与可信入口确定。

## 执行要求
决定卡先说明本方案是在等本人决定还是本轮已经结束但未完成。等待批准时不执行；独立验收拒收时展示具体卡点，不能用成功验收所需的证据字段覆盖拒收原因。验收声称成功时仍须核对完整证据。

- 规划、执行、验收分别领取任务，分别使用新会话。同一阶段中断后保留原会话和实际执行记录，先核实结果，不盲目重做。
- Codex 阶段进程关闭个人生命周期 Hook 和记忆注入，防止会话整理覆盖岗位结果；模型、认证、项目规则及固定沙箱权限保持。其他接单程序继续使用原适配器。
- 方案必须包含具体操作、影响、恢复办法和验收标准。批准绑定工单及方案版本；修改方案后旧批准失效。
- 执行、改期、暂缓和取消由固定控制器处理。自定义文字作为新方案的资料，不能直接当作命令执行。改期使用带时区的明确时间；暂缓后不定时重问。
- 执行完成后由独立验收岗位重新取证。命令退出成功或执行者声称完成都不构成结案依据。
- 结果未知、缺少维护工具或需要本人登录时，列出具体缺口和恢复后的下一步，不使用笼统的“仍需人工维护”。
- 事实检查入口恢复后，尚未执行的任务返回规划或重新确认原方案；已有执行记录的任务先查实际结果，不能重新执行。
- 首版岗位使用 Codex；Claude Code 复用已有适配器，完成后台登录、代理门禁与隔离验收后可替换岗位绑定。

## 本批验收

覆盖正常闭环、原方案批准、方案变更、明确改期、暂缓、取消、重复事件与回答、同批不同任务、重启接续、执行结果未知和验收失败。项目动作使用临时仓库与假系统服务，不为验收安装补丁、重启生产服务或发送真实消息。

## 本人任务与交接证据

项目可登记 `requests: {source, type}`，把已授权来源的一类事件作为本人任务。主 Agent 使用现有 `emit` 入口提交，`detail` 只包含 `goal`、`deliverable`、`acceptance`，以及可选的 `dueAt` 和 `completion`。三项正文必须非空；`dueAt` 使用含时区的 ISO 时间；`completion` 为 `delivery` 或 `effect`，默认 `delivery`。正文只作为资料，项目、岗位、程序、权限、目录和验收入口仍取可信配置。无法确定项目或完成标准时先询问本人，不猜测执行范围。

任务保留目标、约定交付物、完成标准、原检查时间和方案版本。总控分别记录收到执行结果、独立验收、下游使用或业务效果；收到结果不等于验收通过。项目验收返回的证据必须包含 `version`、`location`、`environment`，分别指向实际版本或指纹、证据位置和执行环境；通用控制器核对字段，项目入口负责验证对应事实。旧配置和旧工单没有契约时继续按原完成范围运行。

可信配置可用 `contracts: true` 为新故障工单启用项目提供的契约，项目的 `inspect` 返回同结构 `contract`。旧工单保持原语义，不补写历史事实。

`completion: effect` 的任务在交付验收通过后等待原业务恢复证据，不占进程，不通过重跑正式业务取证。需要人使用而无法观察的成果保持待确认。修改方案清除旧批准、旧结果和旧验收。检查时间到期后复用中台定时，报告当前未完状态；暂缓、取消或完成后撤销该检查，不新增后台轮询。

默认仍由本人批准执行。可信配置可设置 `approval: read-only`，仅允许三个模型岗位都为 `read` 的任务自动从规划转入只读执行；项目入口必须保证自身动作只读。该设置不扩大固定脚本的权限，也不允许事件选择批准策略。审核检查具体成果，落实检查沿原工单和业务回执取证，复盘按实际任务需要开展，不增加固定审批层。

协作方法改写自 Solo to Team，来源与许可见[协作方法来源](协作方法来源.md)。

## 配置与接入

规划输出可增加一个最多120字的 `summary`，只写拟做什么、关键影响和需要本人决定什么；完整的 `steps`、`impact`、`rollback`、`acceptance` 继续保留。旧方案没有 `summary` 时，从操作和影响生成短说明，仍需原批准与验收。决定卡将短说明与完整方案分开；项目名称映射、折叠和结案展示见[飞书卡片展示](protocol.md#飞书卡片展示)。

项目保存一个维护 JSON 配置，包含 `id`、相对配置文件的 `root`、相对项目的私有 `state`、`worker`、事件匹配 `when`、固定项目入口 `hook` 和三个岗位 `roles.plan/execute/verify`。岗位的 `use` 使用现有 `codex`、`claude` 或 `command` 适配器；规划和验收只允许 `access: read`，执行可为 `edit`。需要代理门禁时，`program` 指向经过验证的 CLI 包装器；它与岗位所选 CLI 必须匹配。

在已安装插件的源码或程序目录执行 `node plugins/maintenance/run.ts <项目配置文件> rules` 生成规则片段，再通过现有规则入口登记。安装目录的 `plugins/maintenance/` 可覆盖随程序附带的版本；所有接此岗位的 worker 必须使用已验证的同版插件。该命令不修改配置、不启用规则、不发事件。

项目入口以固定命令启动，从标准输入接收 `{stage, task, root}`，只向标准输出写 JSON。`inspect` 返回 `active/resolved/blocked`、脱敏事实和具体说明；`prepare` 在批准后准备隔离工作区；`plan/execute/verify` 返回固定 `cwd`、可信岗位要求和独立证据，或确定性的 `result`；`executed/verified/accept/status` 根据实际记录返回 `ok` 和 `summary`。这些入口不得从资料中执行命令。

`state/flow.json` 只保存维护工单、方案版本和待交回执，不另行排队或定时。阶段结果、执行启动标记与必要证据保留在工单目录。项目只有在原进程已结束、结果明确且允许接续时才能返回 `resumable: true`；用户选择“继续本阶段”后使用原候选、原会话和新的阶段尝试编号。结果未知时只走 `status`，不能把“没读到结果”当成未执行。

暂缓后，可通过现有本人入口 `agent-autoloop run maintenance-<id>-coordinate --subject <工单编号>` 恢复决定卡。该操作先核对现状，不等于批准执行。改期填写明确的未来 ISO 时间及其时区；到期使用中台复查，先核对原方案是否仍适用。阶段交接继续受8层上限约束，不允许通过换编号或清零绕过。
